# خطة مراجعة وتحسين نظام المصادقة والـ API

## ملخص المراجعة
مراجعة شاملة لنظام المصادقة وواجهات الـ API في المشروع، مع تحديد المشاكل الحرجة وال Priority fixes.

---

## المشاكل الحرجة (Critical) — يجب إصلاحها فوراً

### 1. ثغرة Open Redirect في OAuth Callback
**الملف:** `src/app/api/auth/callback/route.ts:20,174`

المعلمة `next` تُستخدم مباشرة في `NextResponse.redirect()` بدون تحقق:
```typescript
const next = searchParams.get('next') || '/'
return NextResponse.redirect(new URL(next, baseUrl))
```
مهاجم ي Craft URL مثل `/api/auth/callback?code=...&next=https://evil.com` يُحوّل المستخدم لموقع ضار بعد تسجيل الدخول.

**الإصلاح:** التحقق من أن `next` مسار نسبي فقط:
```typescript
if (!next.startsWith('/') || next.startsWith('//')) {
  next = '/'
}
```

### 2. Telegram Auth يستخدم filesystem — مكسور في Serverless
**الملف:** `src/app/api/auth/telegram/route.ts`

الـ sessions تُحفظ في `.tmp/telegram-sessions/` على القرص. في Vercel (serverless):
- POST ينشئ ملف في invocation واحدة
- GET يقرأ في invocation مختلفة (قد لا يجد الملف)
- **النتيجة:** تسجيل الدخول عبر Telegram غير موثوق في الإنتاج

**الإصلاح:** نقل Telegram sessions إلى Redis (مثل webhook handler).

### 3. Telegram Webhook بدون تحقق من Telegram
**الملف:** `src/app/api/auth/telegram/webhook/route.ts`

الـ endpoint يقبل أي POST بدون التحقق من أنه جاء فعلاً من Telegram. يمكن تزوير طلب webhook للتسجيل كأي مستخدم Telegram.

**الإصلاح:** التحقق من `X-Telegram-Bot-Api-Secret-Token` header.

### 4. Telegram Webhook و Polling يستخدمان storage مختلف
**الملف:** `src/app/api/auth/telegram/webhook/route.ts` vs `src/app/api/auth/telegram/poll/route.ts`

- Webhook يحفظ في **Redis** (`telegram_auth:${sessionToken}`)
- Polling يقرأ من **filesystem** (`.tmp/telegram-sessions/`)

**هذه متسقة بشكل أساسي** — webhook لا يمكن أن يصلح polling.

### 5. N+1 Query في Admin Analytics
**الملف:** `src/app/api/admin/users/analytics/trends/route.ts`

يُحلق عبر N يوم وينفذ 2 طلبات DB لكل يوم. لـ 90 يوم = **180 طلب DB منفرد**.

**الإصلاح:** استعلام واحد مُجمّع مع `GROUP BY`.

## مشاكل عالية الأولوية (High Priority)

### 6. `/api/admin/setup` بدون تحقق server-side
**الملف:** `src/app/api/admin/setup/route.ts`

لا يستخدم `requireOwner()` أو أي helper مصادقة. أي مستخدم moderator+ يمكنه تفعيل setup.

**الإصلاح:** إضافة `await requireOwner()` أو على الأقل التحقق من عدم وجود owner.

### 7. لا يوجد استخدام لـ Zod في أي route admin
جميع 48 route في `src/app/api/admin/` تستخدم validation يدوي. لا يوجد Zod schemas.

**الإصلاح:** إنشاء schemas مشتركة في `src/lib/schemas/` واستخدامها.

### 8. Bug في slug comparison
**الملف:** `src/app/api/admin/mods/[id]/route.ts:99`
```typescript
if (body.slug && body.slug !== existing) // ← يقارن string بـ object!
```
**الإصلاح:** `body.slug !== existing.slug`

### 9. صلاحية الحذف غير متسقة
- Games/Mods: تتطلب `canDelete()` (admin+)
- Teams/Series/News/Ads: أي moderator يقدر يحذف

**الإصلاح:** توحيد الصلاحيات — إضافة `canDelete()` للجميع.

### 10. جميع الـ 20 view مستوردة eagerly (بدون code splitting)
**الملف:** `src/app/page.tsx`

كل المكونات (بما فيها ModDetailPage, UploadPage, SettingsPage) تُحمّل في الـ initial bundle.

**الإصلاح:** استخدام `next/dynamic` لـ lazy loading.

### 11. Bookmark check ينطلق لكل ModCard
**الملف:** `src/components/mod-card.tsx:111-116`

كل ModCard يستدعي `/api/bookmarks/check` عند التحميل. في الصفحة الرئيسية مع 50+ card = **50+ API call**.

**الصلاح:** Batch bookmarks check أو client-side cache.

### 12. Hero Slider يسبب 60 re-render/ثانية
**الملف:** `src/components/hero-slider.tsx:84-93`

`requestAnimationFrame` يحدّث React state على كل frame.

**الإصلاح:** استخدام DOM ref بدلاً من React state للـ progress bar.
